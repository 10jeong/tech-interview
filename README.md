## 객체지향 (OOP)
<details markdown="1">

    <ul>
      <li>인터페이스는 동작할 기능을 담은 명세서이고, 
추상 클래스는 공통되는 코드를 담은 클래스입니다.

인터페이스의 경우 확장에는 열려있고 변경에는 닫혀있다는 OCP 원칙에 따라 변경이 잦은 로직에 적합하고, 추상 클래스는 상속의 이점을 사용하여 공통적인 코드가 중복으로 작성되는 경우를 방지하는 데에 적합합니다.

+(경험)</li>
    </ul>
  </div>
</details>

      </li>
    </ul>

<details markdown="1">
  <summary>Class와 Object에 대해 설명해주세요.</summary>
  <div>
    <ul>
      <li>java의 Object는 모든 클래스의 부모 클래스입니다. 컴파일러가 자동으로 extends Object를 추가합니다.
클래스는 필드와 메서드로 구성되어 있습니다.
클래스는 객체를 생성하기 위한 설계도라는 설명도 있지만 반드시 그렇지는 않습니다.
Collection와 같이 클래스멤버 메소드로만 이루어진 경우가 있습니다.
객체(Object)는 속성과 동작으로 이루어진 것들을 포함하는 개념입니다.
java한정 클래스가 인스턴스된 것을 객체라고 할 수 있습니다.
      </li>
    </ul>
  </div>
</details> 

<details markdown="1">
  <summary>Encapsulation(캡슐화)이란 무엇인가요?</summary>
  <div>
    <ul>
      <li>캡슐화는 관련된 기능과 데이터를 클래스라는 캡슐에 모으고 외부에서 내부 구현을 직접 알 수 없도록 은닉하는 것입니다. java에서는 필드에 private을 붙여 외부에서 접근할 수 없도록 하고, 생성자나 getter, setter를 이용해 접근창구를 하나로 통일하도록 설계합니다.
캡슐화를 통해서 응집도는 높히고 결합도는 낮춰, 내부 구현이 바뀌어도 외부 코드로 전파되는 영향을 최소화 합니다. 
      </li>
    </ul>
  </div>
</details> 

<details markdown="1">
  <summary>다형성(Polymorphism)을 프로젝트에서 어떻게 활용했는지 예를 들어 설명해주세요.</summary>
  <div>
    <ul>
      <li>
프로젝트에서 상태 변경 검증 메서드를 추상화하여, 실제 상태 객체에 따라 서로 다른 검증 로직이 수행되도록 구성한 경험이 있습니다.
특히 동일한 메서드를 호출하더라도 각 상태 객체에서 오버라이딩된 메서드가 실행되도록 구현하면서, 런타임 시점에 실제 객체의 메서드가 선택되는 동적 바인딩 기반의 다형성 구조를 직접 경험할 수 있었습니다.
      </li>
    </ul>
  </div>
</details> 

<details markdown="1">
  <summary>상속의 개념을 설명하고, 상속의 장단점을 이야기해 주세요.</summary>
  <div>
    <ul>
      <li>
        기존 클래스의 필드와 메서드를 새로운 클래스가 물려받아 기능을 확장하고 재사용할 수 있게 하는 객체지향 프로그래밍의 핵심 메커니즘입니다. 장점으로는 공통 로직의 중복을 제거하여 코드를 간결하게 유지할 수 있으며, 상위 타입으로 묶는 업캐스팅을 통해 다형성을 효과적으로 구현할 수 있습니다. 
        부모와 자식 클래스가 강한 결합으로 묶입니다. 부모 클래스의 작은 변경이 모든 자식 클래스에 치명적인 영향을 미칠 수 있으며, 자바는 단일 상속만 지원하므로 아키텍처 확장성에 제한이 생깁니다. 
      </li>
    </ul>
  </div>
</details> 

<details markdown="1">
  <summary>상속 대신 조합을 사용하는 것이 적합한 경우는 언제인가요?</summary>
  <div>
    <ul>
      <li>
        클래스 간의 관계가 구체적인 포함 관계인 has-A 관계일 때 적합합니다.
        런타임에 동적으로 동작을 변경해야 할 때 필수적입니다. 상속은 컴파일 시점에 관계가 고정되지만, 조합은 실행 중에 주입된 객체를 교체하여 유연하게 대응할 수 있습니다.
        부모 클래스의 특정 구현 로직만 안전하게 재사용하고 싶을 때 사용합니다. 상속은 불필요한 public 메서드까지 자식에게 강제로 노출시켜 캡슐화를 깨뜨리지만 조합은 필요한 기능만 내부에서 호출하므로 안전한 것 같습니다.
      </li>
    </ul>
  </div>
</details> 

<details markdown="1">
  <summary>디자인 패턴 중 싱글톤(Singleton) 패턴을 설명하고, 실제로 구현할 때 고려해야 할 사항을 이야기해주세요.</summary>
  <div>
    <ul>
      <li>
        싱글톤 패턴이란, 클래스의 객체를 한 개만 생성하여 전역으로 사용하는 디자인 패턴입니다.
        예를 들어 Spring Bean처럼, 애플리케이션 전체에서 동일한 값을 공유해야 하는 객체에 싱글톤 패턴을 사용할 수 있습니다.
        싱글톤 패턴을 구현할 때에는 멀티 스레드 환경에서 동시에 여러 객체가 생성되는 동시성 문제가 발생할 수 있기 때문에, Lazy Holder나 ENUM 방식을 사용합니다.
        Lazy Holder는 중첩 클래스로 구현합니다. 내부 클래스가 호출되는 경우 한 번만 초기화되기 때문에 동시성 문제를 방지할 수 있습니다. 다만, 자바의 리플렉션 기능을 사용하면 객체를 추가로 생성할 수 있어 완전히 방어되지는 않습니다.
        ENUM을 사용하는 경우, JVM에 의해 ENUM 상수가 최초 한 번만 생성되는 것을 보장하기 때문에 동시성이나 리플렉션 문제에서 안정적입니다.
      </li>
    </ul>
  </div>
</details>

  <summary>의존성 주입(Dependency Injection)이란 무엇이며, 이를 적용했을 때의 장점을 설명해주세요.</summary>

## 데이터베이스 (Database)
<details markdown="1">
  <summary>정규화와 역정규화의 차이를 설명해주세요.</summary>
  <div>
    <ul>
      <li>
        정규화는 데이터 중복을 제거하여 무결성을 높이는 설계 방식이고, 
        역정규화는 조회 성능 향상을 위해 중복을 허용하는 설계 방식입니다. 
        정규화는 데이터 정합성에 유리하지만 JOIN이 증가할 수 있고, 
        역정규화는 조회 성능은 좋아지지만 데이터 동기화 비용이 발생하는 트레이드오프가 있습니다.
      </li>
    </ul>
  </div>
</details> 

<details markdown="1">
  <summary>RDB와 NoSQL의 차이점을 설명해주세요.</summary>
  <div>
    <ul>
      <li>
rdb는 관계형 데이터 베이스로 고정된 스키마, 테이블 구조 형식을 띄고 있고 sql이라는 구조화된 질의를 사용합니다.
주된 장점으로는 트랜잭션의 원자성과 일관성에 따른 데이터 무결성을 보장합니다.<br>
nosql은 not only sql로 key-value, document 같이 유연한 스키마를 가지고, sql 대신 전용 쿼리, api 등으로 질의 합니다.
rdb보다 높은 쓰기 성능을 위해 사용하기도 하고, 특히 현대 웹개발에서는 고정된 테이블 구조에 맞추기 어려운 비정형 데이터를 저장하는 목적으로 사용 합니다.<br>
RDB는 고정된 스키마를 가져 스키마 변경시 큰 비용이 발생하고, nosql은 스키마가 유연하지만 데이터 정합성 관리가 어렵기 때문에 트레이드오프를 고려해서 서비스의 요구사항에 따라 개발자가 선택해야 합니다.
      </li>
    </ul>
  </div>
</details> 
<details markdown="1">
  <summary>인덱스를 사용하는 이유와 성능 영향을 설명해주세요.</summary>
  <div>
    <ul>
      <li>
​데이터베이스 인덱스의 핵심 목적은 조회 성능 최적화입니다. 대량의 데이터에서 특정 레코드를 신속하게 찾아내 순차 스캔을 방지하고, 이를 통해 CPU 자원의 연산량을 획기적으로 줄여줍니다. <br>
하지만 읽기 성능이 향상되는 만큼 쓰기 오버헤드라는 부작용이 존재합니다. 데이터의 삽입, 수정, 삭제가 일어날 때마다 인덱스 구조도 매번 함께 갱신해야 하므로, 인덱스가 과도하면 쓰기 증폭 현상으로 인해 오히려 전체적인 시스템 성능이 저하될 수 있습니다
      </li>
    </ul>
  </div>
</details> 
<details markdown="1">
  <summary>JOIN의 개념과 사용 사례를 설명해주세요.</summary>
  <div>
    <ul>
      <li>
JOIN이란, 데이터를 검색하기 위해 두 개 이상의 테이블을 연결하는 방법입니다. 검색하는 상황에 따라 INNER JOIN, OUTER JOIN, CROSS JOIN 등을 사용할 수 있습니다. JOIN을 설계할 때는, 탐색하는 데이터의 양이나 방법에 따라 성능이 좌우될 수 있기 때문에 JOIN하려는 컬럼에 인덱스를 걸거나 JOIN 테이블의 순서를 조절하면서 성능을 높일 수 있습니다.</li>
      </li>
    </ul>
  </div>
</details> 
<details markdown="1">
  <summary>외래 키(Foreign Key)와 참조 무결성을 설명해주세요.</summary>
  <div>
    <ul>
      <li>
외래 키는 한 테이블의 컬럼이 다른 테이블의 기본 키를 참조하도록 설정하는 제약조건입니다.
이를 통해 참조 무결성을 보장할 수 있으며, 존재하지 않는 데이터를 참조하는 것을 방지합니다. 
장점은 데이터 정합성을 DB 레벨에서 강하게 보장할 수 있다는 점이고,
단점은 쓰기 성능 부담과 테이블 간 결합도가 높아질 수 있다는 점입니다.</li>

<li>
참조 무결성이란 외래 키를 통해 연결된 데이터 간의 관계가 항상 유효하도록 보장하는 제약 조건입니다.
즉, 자식 테이블의 외래 키는 반드시 부모 테이블에 존재하는 값을 참조해야 하며, 존재하지 않는 데이터를 참조할 수 없습니다.
예를 들어 주문상세가 주문을 참조하고 있을 때, 존재하지 않는 주문 ID를 저장하거나 참조 중인 주문을 임의로 삭제하여 데이터 관계가 깨지는 것을 방지하는 것입니다.</li>
<li>
외래 키는 관계를 만드는 제약조건이고, 참조 무결성은 그 관계가 깨지지 않도록 보장하는 원칙입니다.</li>
      </li>
    </ul>
  </div>
</details>
<details markdown="1">
  <summary>데드락(Deadlock)을 방지하는 방법을 설명해주세요.</summary>
  <div>
    <ul>
      <li>
데이터베이스 데드락은 여러 트랜잭션이 서로가 보유한 락이 해제되기를 기다리면서 무한 대기하는 상황입니다.
예방 방법으로는 트랜잭션 간 락 획득 순서를 통일해서 순환 대기가 발생하지 않도하는 것이 대표적입니다.
데드락이 발생하면 DBMS가 이를 탐지한 뒤 한쪽 트랜잭션을 롤백시키며, 애플리케이션에서는 예외를 처리하고 재시도하는 방식으로 대응할 수 있습니다.
      </li>
    </ul>
  </div>
</details> 
<details markdown="1">
  <summary>트랜잭션(Transaction)과 ACID 특성을 설명해주세요.</summary>
  <div>
    <ul>
      <li>
트랜잭션은 데이터베이스의 여러 작업을 하나의 단위로 묶은 것을 뜻 합니다. 트랜잭션은 ACID 특성을 가지는데, 작업 전체가 Commit 되거나 Rollback 되어야 하고 트랜잭션 전후에 데이터 무결성이 유지돼야 합니다. 또 동시에 실행되는 트랜잭션 간 간섭을 제어하고 Commit 된 결과는 장애 이후에도 보존되는 것을 의미합니다.

제가 실제로 체감했던 부분은 도메인의 상태 변경과 Outbox 이벤트 저장을 같은 트랜잭션으로 묶어 상태만 변경되거나 이벤트만 저장되는 상황을 방지할 수 있었습니다.
      </li>
    </ul>
  </div>
</details> 


##  백엔드 프레임워크
<details markdown="1">
  <summary>Legacy Spring과 Spring boot의 차이를 설명해주세요</summary>
  <div>
    <ul>
      <li>
Legacy Spring과 Spring Boot의 가장 큰 차이는 '설정의 자동화'와 '실행 환경의 간편함'입니다.  <br/>
        Legacy Spring은 개발자가 모든 설정(XML/Java)을 수동으로 관리하고 외장 WAS를 별도로 구축해야 하므로 초기 환경 설정이 매우 복잡합니다. <br/>
        반면, Spring Boot는 'Auto Configuration'을 통해 설정을 자동화하고 내장 서버를 포함하여, 설정 과정 없이 즉시 애플리케이션 실행이 가능합니다. <br/>
        결과적으로 Spring Boot는 개발자가 인프라 설정이 아닌 비즈니스 로직에만 집중하게 하여, 개발주기를 단축하고 시스템 신뢰성을 높여줍니다.</li>
      </li>
    </ul>
  </div>
</details>
<details markdown="1">
  <summary>AOP가 무엇이며 Spring에서 어떻게 구현하는지 설명해주세요.</summary>
  <div>
    <ul>

<li>
AOP는 관점 지향 프로그래밍으로, 로깅·트랜잭션·권한 검사와 같이 여러 객체에서 공통적으로 사용되는 기능을 비즈니스 로직과 분리하기 위한 기술입니다.

Spring에서는 @Aspect를 사용해 공통 기능을 정의하고, @Before, @After, @Around 등의 어노테이션을 통해 특정 메서드 실행 전후에 공통 로직을 적용할 수 있습니다.

실제로 저는 직접 Aspect를 구현한 경험은 없지만, @Transactional을 사용하며 AOP를 활용한 경험이 있습니다. @Transactional 역시 Spring AOP를 기반으로 동작하며, 메서드 호출 시 트랜잭션 시작과 커밋 또는 롤백 같은 공통 기능을 비즈니스 로직과 분리하여 처리합니다.</li>
    </ul>
  </div>
</details> 
<details markdown="1">
  <summary>JPA와 Hibernate의 차이를 설명해주세요.</summary>

        JPA로 ORM에 필요한 기능을 정의하면, Hibernate는 이를 구현하여 SQL 생성이나 영속성 관리 등을 수행합니다.</li>
      </li>
    </ul>

  </summary>
  <div>
    <ul>
      <li>
        네, 스프링 DI는 객체가 직접 의존성을 생성하지 않고 Ioc 컨테이너가 빈의 생명주기를 관리하며 외부에서 의존성을 주입해주는 기술입니다. <br/>
        이를 사용하는 주된 이유는 객체 간의 결합도를 낮추기 위해서입니다. 구체적으로는 다음과 같은 이유로 사용됩니다. <br/>
첫째, 객체가 인터페이스에만 의존하게 되어 구현체 변경이 쉬워집니다. <br/>
둘째, Mock(가짜) 객체를 주입할 수 있어 단위 테스트 환경을 구축하기 편리합니다. <br/>
마지막으로 생성과 사용을 분리함으로써,  기존 코드 수정 없이 새로운 구현체로 기능 확장이 가능합니다.  이는 객체 지향 원칙인 개방 폐쇄 원칙을 준수합니다. <br/>

이러한 장점 덕분에 개발자가 복잡한 의존 관계를 다루지 않고 비즈니스 로직에만 집중할 수 있게 도와줍니다.
      </li>

또한 @PostConstruct와 @PreDestroy를 사용하면 Bean 생성 후 또는 소멸 전에 필요한 작업을 수행할 수 있습니다.

<details>
  <summary>
    @Transactional의 역할을 설명해주세요.
  </summary>
  <div>
    <ul>
      <li>
@Transactional은 비즈니스 로직을 하나의 트랜잭션 단위로 묶어 데이터 무결성을 보장하는 어노테이션입니다. 역할을 말씀드리면 다음과 같습니다. 

첫째, 스프링은 AOP를 통해 프록시 객체를 생성하고, 메서드 실행 전후로 트랜잭션의 시작과 종료를 자동으로 처리합니다. 덕분에 개발자는 begin, commit, rollback 같은 복잡한 코드를 직접 작성할 필요 없이 비즈니스 로직에만 집중할 수 있습니다. <br/>

둘째, ACID 원칙을 준수하여, 메서드 내의 모든 작업이 성공하면 커밋하고 하나라도 실패하면 전체를 롤백하여 데이터가 중간에 꼬이지 않도록 합니다. <br/>

셋째, 격리 수준(Isolation Level)과 전파(Propagation) 속성을 설정해 다중 요청 환경에서 발생하는 데이터 간섭을 방지하고, 각 요청이 독립적인 트랜잭션 단위로 처리되게 함으로써 안정성을 보장합니다. <br/>

한마디로 Transactional 어노테이션은 AOP 기술을 활용해 데이터베이스 리소스 제어를 표준화하고, 안정적인 서비스 운영을 가능하게 하는 안전장치라고 할 수 있습니다.
      </li>
    </ul>
  </div>
</details>

저는 JWT 기반 인증을 구현하면서 Security Filter Chain에 커스텀 필터를 추가해 토큰을 검증했고, 검증된 사용자 정보를 Authentication 객체로 생성하여 SecurityContext에 저장한 뒤 인가 처리에 활용한 경험이 있습니다.
      </li>
    </ul>

## API 설계 및 통신
<details markdown="1">
  <summary>REST와 SOAP의 차이를 설명해주세요.</summary>
  <div>
    <ul>

<li>
SOAP와 REST는 둘 다 다른 애플리케이션과 소통하기 위해 만들어진 규칙입니다. SOAP의 경우, 통신 규칙을 엄격하게 정의하여 데이터의 무결성이나 보안을 보장할 수 있고, REST의 경우, 무상태나 캐싱을 적용하여 확장성을 높이는 방식입니다. 따라서 높은 수준의 보안이 필요한 경우 SOAP가 적합하고, 일반적인 웹 개발에서는 접근성과 확장성이 좋은 REST를 사용합니다.</li>
    </ul>
  </div>
</details>

<details markdown="1">
  <summary>RESTful API 설계 원칙을 설명해주세요.</summary>
  <div>
    <ul>

<li>
RESTful API 설계 원칙은 REST 아키텍처의 제약 조건을 따르면서 API를 설계하는 것입니다.

대표적으로 자원(Resource)은 URI로 표현하고 행위(Action)는 HTTP Method로 구분합니다.
또한 Stateless 원칙에 따라 서버는 클라이언트의 상태를 저장하지 않아 확장성을 높일 수 있으며, 일관된 인터페이스를 제공하여 직관적이고 확장 가능한 API를 설계합니다.</li>
    </ul>
  </div>
</details>

<details markdown="1">
  <summary>API 버전 관리의 중요성과 방법을 설명해주세요</summary>
  <div>
    <ul>
      <li>
        API 버전 관리는 기존 클라이언트에 영향을 주지 않으면서 서비스를 지속적으로 확장하기 위한 필수 전략입니다. 핵심 목적은 시스템 개편 시 발생할 수 있는 서비스 중단을 방지하고, 하위 호환성을 안정적으로 유지하는 데 있습니다. <br/>

구현 방법으로는 직관적이고 캐싱에 유리한 URI 방식과, URL을 깔끔하게 유지할 수 있는 헤더, 파라미터, Mime Type 방식이 있습니다. 최근 Spring 7에서는 `ApiVersionStrategy` 인터페이스라는 버전 관리를 정식 지원하여, 애플리케이션 전체에 일관된 버저닝 정책을 더욱 쉽게 적용할 수 있게 되었습니다. <br/>

실무 전략으로는 전체 서비스의 일관성을 위한 글로벌 버저닝을 기본으로 하되, 특정 리소스의 변경이 잦은 대규모 환경에서는 클라이언트별로 특정 버전을 고정해 제공하는 개별 리소스 버저닝을 하이브리드로 채택하여 유연성을 높이고 있습니다.
      </li>
    </ul>
  </div>
</details>

<details markdown="1">
  <summary>@Controller와@RestController차이점이 무엇인가요?</summary>
  <div>

        @RestController는 REST API를 만들 때 사용하며, 반환 객체를 JSON이나 XML로 변환해 HTTP Response Body에 바로 응답합니다.
        @RestController는 @Controller와 @ResponseBody를 합친 형태입니다.
      </li>
    </ul>
  </div>

<details markdown="1">
  <summary>HTTP 상태 코드(200/404/500) 차이를 설명해주세요</summary>
  <div>
    <ul>
      <li>
        HTTP 상태 코드는 서버가 클라이언트의 요청을 처리한 결과를 나타내는 표준 응답 코드입니다.
        200번대는 요청이 정상적으로 처리된 경우를 의미하고, 400번대는 클라이언트의 요청에 문제가 있는 경우를 의미합니다. 대표적으로 404 Not Found는 요청한 리소스가 존재하지 않을 때 반환됩니다. 반면 500번대는 서버 내부에서 예외가 발생해 요청을 처리하지 못한 경우를 의미합니다.
      </li>
    </ul>
  </div>
</details>

<details markdown="1">
  <summary>멱등성(Idempotency)을 설명해주세요</summary>
  <div>
    <ul>
      <li>
        멱등성이란, 요청을 여러 번 보내더라도 한 번만 처리된 것처럼 보이게 만드는 성질입니다. API 측면에서 POST나 PATCH와 같이 데이터 수정이 일어날 수 있는 메서드는 멱등하지 않기 때문에 개발 시에 멱등키처럼 동일한 요청을 식별할 수 있는 멱등성 처리가 필요합니다. 구현해본 경험으로는, 결제 파트 개발 시 결제 승인이 중복으로 처리되지 않도록 기존 결제건의 상태값 기준으로 분기하여 이미 처리한 요청은 기존 응답과 동일하게 반환하도록 처리한 경험이 있습니다.
      </li>
    </ul>
  </div>
</details>
<details markdown="1">
  <summary>GraphQL과 REST API 차이를 설명해주세요.</summary>
  <div>
    <ul>
      <li>
GraphQL과 REST API의 가장 큰 차이는 데이터 요청의 주도권과 엔드포인트 구조에 있습니다. REST API는 서버가 정의한 고정된 리소스를 다중 엔드포인트를 통해 가져오는 반면, GraphQL은 단일 엔드포인트에서 클라이언트가 필요한 데이터만 직접 쿼리하여 가져옵니다. 따라서, 웹, 모바일 IoT 등 데이터 요구사항이 서로 다른 여러 클라이언트 유형이 존재할 때 복잡한 쿼리 및 조인 작업에서 GraphQL이 강렬한 성능을 발휘하고, 표준화된 통신 규격과 강력한 HTTP 캐싱이 필요한 공공 API나 대규모 시스템 연동에는 REST API가 더 적합합니다.
      </li>
    </ul>
  </div>
</details>

  <summary>HTTP/2와 HTTP/1.1 차이를 설명해주세요.</summary>
  <div>
    <ul>
      <li>
HTTP/1.1은 첫 표준으로 지정된 HTTP 프로토콜입니다. 이전에 HTTP 프로토콜이 개발되며 모호했던 지점들을 개선하여 표준 버전으로 개편하였습니다. 예를 들어 통신 과정에서 사용한 Connection을 재사용하거나, 파이프라이닝의 추가로 앞선 요청의 응답을 기다리지 않고도 여러 요청을 전송할 수 있도록 구성하였습니다.
HTTP/2는 더 효율적이고 빠른 프로토콜 구현을 위해 2015년에 새로 지정된 표준입니다. 기존 HTTP/1.1에 선행 파일이 늦어질수록 지연 시간이 증가하는 HOL 블로킹이라는 문제점을 해결하기 위해 하나의 Connection에서 여러 요청과 응답을 병렬적으로 처리할 수 있도록 개선된 형태입니다.
      </li>
    </ul>

저는 프로젝트에서 Swagger를 사용했는데, 개발 단계에서 API를 바로 확인하고 테스트할 수 있어 협업에 유리했기 때문입니다.

  <div>
    <ul>

<li>
HATEOAS는 REST 아키텍처의 제약 조건 중 하나로, 하이퍼미디어를 통해 애플리케이션의 상태를 전이시키는 원리입니다. 서버가 리소스 응답 시 다음에 수행 가능한 행동들에 대한 링크 정보를 함께 제공함으로써, 클라이언트가 서버의 엔드포인트 구조를 미리 다 알지 못해도 동적으로 서비스를 탐색할 수 있게 합니다 이를 통해 클라이언트와 서버 간의 결합도를 낮추어 서버의 리소스 경로가 바뀌어도 클라이언트가 영향을 받지 않는 장점이 있습니다. 다만, 응답 데이터 용량의 증가와 서버 측 구현 복잡도라는 트레이드 오프가 존재하므로, 무분별한 적용보다는 상태 흐름이 정교하게 제어되어야 하는 경우 도입하는 게 좋을 것 같습니다.
  .</li>

  <div>
    <ul>

<li>
OAuth 2.0은 인증이 아니라 권한 부여를 위한 프로토콜입니다. Resource Owner, Client, Authorization Server, Resource Server 4가지 역할로 구성되고, 가장 널리 쓰이는 Authorization Code Grant 방식에서는 사용자가 Authorization Server에서 로그인·동의하면 Authorization Code를 발급받고, Client의 백엔드가 이 Code와 client_secret을 함께 보내 Access Token으로 교환합니다. 이렇게 하면 Access Token이 브라우저를 거치지 않아서 탈취 위험이 줄어듭니다.
</li>
    </ul>
  </div>
</details>

##  성능 최적화 및 캐싱
<details markdown="1">
  <summary>캐시(Cache) 메커니즘과 사용하는 이유를 설명해주세요.</summary>
  <div>
    <ul>
      <li>
캐시는 자주 사용되는 데이터를 원본 저장소보다 빠른 메모리 공간에 저장하여 효율을 높이는 방식입니다. 요청이 들어온 경우, 캐시를 우선적으로 확인하는데, 캐시에 데이터가 있는 경우를 Cache Hit라고 하며, 이 경우 캐시에서 바로 데이터를 반환합니다. 캐시에 데이터가 없는 경우는 Cache Miss라고 하며, 이 때에는 DB와 같은 원본 저장소에 접근하여 데이터를 찾아 반환하게 됩니다.
      </li>
    </ul>
  </div>
</details>
<details markdown="1">
  <summary>CDN이 성능 최적화에 어떤 기여를 하는지 설명해주세요.</summary>
  <div>
    <ul>
      <li>
CDN은 전 세계에 분산된 캐시 서버를 배치해 사용자와의 물리적 거리를 단축함으로써 네트워크 지연시간을 줄이고 서비스 성능을 최적화합니다. 이를 통해 정적 콘텐츠를 오리진 서버 대신 엣지 노드에서 직접 제공함으로써 원본 서버의 트래픽 부하와 대역폭 소모를 방지하여 웹 서비스의 가용성을 확보할 수 있습니다. 
      </li>
    </ul>
  </div>
</details>

<details markdown="1">
  <summary>데이터베이스 쿼리 최적화 방법을 설명해주세요.</summary>
  <div>
    <ul>
      <li>
데이터베이스 쿼리 최적화는 동일한 결과를 더 적은 비용으로 조회하도록 만드는 과정이라고 생각합니다.
개인 프로젝트에서 약 400만 건의 데이터를 대상으로 날짜별 게시글 개수를 조회하는 기능을 구현하면서, 조회 쿼리가 1초 이상 걸리는 문제를 해결한 경험이 있습니다.
memberId를 단일 인덱스로 걸었을 때는 값의 카디널리티가 낮아서 오히려 성능이 더 나빠졌고, createdDate를 단일 인덱스로 걸었을 때는 대체로 빨랐지만 데이터가 없는 memberId로 조회할 경우엔 성능이 떨어지는 걸 확인했습니다. 이걸 해결하려고 memberId와 createdDate를 묶은 복합 인덱스를 적용했더니 30~80ms 수준까지 개선됐습니다.
이 경험으로, 쿼리 최적화는 단순히 인덱스를 추가하는 게 아니라 실행 계획과 데이터 분포를 함께 분석해서 조회 패턴에 맞는 인덱스를 설계하는 게 중요하다는 걸 배웠습니다.
      </li>
    </ul>
  </div>
</details>
<details markdown="1">
  <summary>Redis 데이터 영속성 문제와 해결 방법을 설명해주세요.</summary>
  <div>
    <ul>
      <li>
Redis는 인메모리 데이터베이스이므로 서버가 재시작되거나 장애가 발생하면 메모리에 저장된 데이터가 유실될 수 있는 위험이 있습니다. 따라서 유실 위험을 방지하기 위한 영속성 기능을 제공합니다. 제공되는 기능은 RDB 방식과 AOF 방식이 있습니다. RDB 방식은 Redis의 현재 데이터 상태를 스냅샷으로 저장하는 방식이고, AOF 방식은 Redis에 요청된 모든 쓰기 작업을 로그 파일로 저장하는 방식입니다.
      </li>
    </ul>
  </div>
</details>
<details markdown="1">
  <summary>캐시 무효화 전략에 대해 설명해주세요</summary>
  <div>

      <li>
        캐시 무효화 전략은 데이터의 변경이 발생했을 떄 캐시와 DB의 일관성을 유지하기 위해 기존 캐시를 제거하거나 업데이트하는 핵심 전략입니다. 데이터가 변경될 때 캐시를 비우고 조회 시점에 채우는 Cache-aside 패턴과, 캐시와 DB에 동시에 기록하는 Write-Through와 데이터를 캐시에 먼저 쓴 뒤 비동기적으로 DB에 반영하는 Write-Back 전략이 있습니다. 구체적인 무효화 방법으로는 자동 관리를 위한 TTL(시간 기반 만료)이 가장 널리 쓰이며, 필요에 따라 수동 삭제나 이벤트 기반 무효화를 통해 구현됩니다.

## 보안 및 인증
<details markdown="1">
  <summary>서버 보안의 기본 원칙을 설명해주세요.</summary>
  <div>
    <ul>
      <li>
        서버 보안의 기본 원칙은 정보 보안의 3원칙인 CIA Triad에 기반하여 이루어집니다. 먼저, 기밀성은 인증/인가와 암호화를 통해 허가되지 않은 사용자로부터 데이터를 보호하는 원칙이고, 무결성은 데이터가 손상되거나 변조되지 않도록 유지하는 원칙입니다. 마지막으로 가용성은 인가된 사용자라면 어느 상황에라도 데이터를 이용할 수 있도록하는 원칙입니다.
      </li>
    </ul>
  </div>
</details>

<details markdown="1">
  <summary>쿠키와 세션 차이를 설명해주세요.</summary>
  <div>
    <ul>
      <li>
        쿠키는 클라이언트에 데이터를 저장하는 방식이고, 세션은 서버에 데이터를 저장하고 클라이언트에는 세션 ID만 저장하는 방식입니다. 따라서 세션이 보안성이 높지만 서버 자원을 사용한다는 차이가 있습니다.
      </li>
    </ul>
  </div>
</details>

<details markdown="1">
  <summary>CSRF 공격과 방지 방법을 설명해주세요</summary>
  <div>
    <ul>
      <li>
        CSRF는 사용자가 로그인한 상태를 악용해 사용자가 의도하지 않은 요청을 서버에 보내도록 하는 공격입니다. 브라우저가 쿠키를 자동으로 전송하는 특성을 이용해 발생합니다. 방지 방법으로는 CSRF Token, SameSite Cookie, Origin/Referer 검증 등이 있습니다.
      </li>
    </ul>
  </div>
</details>

<details markdown="1">
  <summary>HTTPS와 SSL 인증서 역할을 설명해주세요</summary>
  <div>
    <ul>
      <li>
        HTTPS란 기존 웹 표준 프로토콜인 HTTP에서 보안 기능을 추가한 프로토콜로, TLS를 이용하여 클라이언트와 서버 간 통신 내용을 암호화합니다. 통신 시작 과정에서 TLS 핸드셰이크 과정을 진행하게 되는데, 이 과정에서 서버는 SSL 인증서를 통해 클라이언트에게 공개 키와 서버의 신원을 증명합니다. 이후 클라이언트가 인증서를 검증한 뒤, 공개키 암호화를 통해 대칭키를 안전하게 교환하고, 실제 데이터 통신은 속도가 빠른 대칭키 암호화를 통해 이루어집니다.
      </li>
    </ul>
  </div>
</details>

<details markdown="1">
  <summary>JWT 기반 인증 방식을 설명해주세요</summary>
  <div>
    <ul>
      <li>
        JWT 기반 인증은 서버가 세션 상태를 저장하지 않고, 토큰 자체에 사용자 인증 정보를 담아 요청을 검증하는 방식입니다. 사용자가 로그인하면 서버는 사용자 ID와 권한 정보가 포함된 JWT를 발급하고, 클라이언트는 이후 요청마다 Authorization 헤더에 Bearer 토큰을 포함합니다. 서버는 JWT의 서명을 검증하여 토큰의 위변조 여부와 만료 시간을 확인하고 인증을 처리합니다.
      </li>
    </ul>
  </div>
</details>

<details markdown="1">
  <summary>CORS와 해결 방법을 설명해주세요</summary>
  <div>
    <ul>
      <li>
        CORS는 웹 브라우저에서 동일한 출처에서의 리소스 접근만을 허용하는 보안 메커니즘인 SOP에서 특정 출처를 허용하기 위한 방법입니다. 기본적으로 브라우저는 SOP를 적용하기 때문에 다른 출처의 응답 사용을 제한합니다. 이때, 특정 출처에서의 요청이 필요한 경우 서버에서 Acess-Control-Allow-Origin 헤더를 설정하여 명시적으로 허용할 출처를 설정하거나, 프록시 서버를 통해 브라우저가 동일한 출처에서 요청하도록 구성하여 CORS 문제를 해결할 수 있습니다.
      </li>
    </ul>
  </div>
</details>
<details markdown="1">
  <summary>XSS 공격과 방지 방법을 설명해주세요.</summary>
  <div>
    <ul>
      <li>
        XSS는 입력 검증 취약점을 악용해 타 사용자의 브라우저에서 악성 스크립트를 실행시키는 보안 위협입니다.
이를 방어하기 위해 모든 유저 입력값에 대해 백엔드 단에서 HTML Escape 및 화이트리스트 기반 필터링을 적용해야 합니다.
또한, 침투 성공 시의 피해를 최소화하도록 중요 토큰은 자바스크립트로 접근이 불가능한 HttpOnly 쿠키에 저장해야 합니다.
이에 더해 브라우저 단에서 승인되지 않은 외부 스크립트 실행을 원천 차단하는 CSP 헤더 설정을 결합하여 다중 방어 체계를 구축하는 것이 중요합니다.
      </li>
    </ul>
  </div>

<details markdown="1">
  <summary>비밀번호 안전 저장 방법을 설명해주세요.</summary>
  <div>
    <ul>
      <li> 비밀번호를 안전하게 저장하기 위해서는 기본적으로 단방향 해시 함수를 사용해야 합니다. 하지만 단순 해시 방식은 동일한 입력값에 대해 항상 동일한 출력값을 가지므로 레인보우 테이블 공격이나 무차별 대입 공격에 매우 취약합니다. 이를 극복하기 위해 사용자 고유의 무작위 문자열을 붙이는 Salting 기법과, 해시 연산을 수천 번 반복하여 해커의 무차별 대입 공격 비용을 늘리는 키 스트레칭 기법을 결합해야 합니다.
      </li>
    </ul>
  </div>

<details markdown="1">
  <summary>SQL Injection과 방지 방법을 설명해주세요.</summary>
  <div>
    <ul>
      <li> SQL Injection은 사용자 입력값이 SQL 문에 그대로 포함되어 의도하지 않은 SQL이 실행되는 공격입니다. 주로 입력값을 문자열로 이어 붙여 SQL을 생성할 때 발생하며, 로그인 우회나 데이터 조회, 삭제 등의 문제가 발생할 수 있습니다. 

이를 방지하기 위해 PreparedStatement를 사용해 SQL과 입력값을 분리하고, 입력값 검증과 최소 권한 원칙을 함께 적용하여 보안을 강화해야합니다
      </li>
    </ul>
  </div>
</details>

## 배포 및 운영
<details markdown="1">
  <summary>CI/CD 파이프라인 구축 경험과 사용 도구를 설명해주세요. CI/CD 구축 후 어떤 개선 효과가 있었나요?</summary>
  <div>
    <ul>
      <li> CI/CD 파이프라인을 구축한 경험으로는 MSA 프로젝트에서 Jenkins를 사용한 경험이 있습니다. Jenkins의 경우 CI/CD 파이프라인에서 대표적으로 사용되기 때문에 관련 문서를 비교적 쉽게 찾을 수 있다는 점에서 선택했습니다. 우선 AWS 배포 환경에서 구성하기 위해 t2.medium 사이즈의 EC2를 하나 띄우고, 이를 Jenkins 서버로 사용하였습니다. CI 과정은 빌드와 테스트를 자동으로 수행하여 문제가 없는지 확인하도록 구성하였고, 빌드와 테스트가 통과하면 Jenkins가 해당 EC2 서버에 자동 배포하도록 구성하였습니다. Jenkins는 초기 설정을 위해 별도 서버를 구성하고 Jenkinsfile 기반으로 파이프라인을 설정하는 점에서 러닝커브가 있었지만, 비용 부담 없이 CI/CD 파이프라인을 구성하여 테스트와 배포를 자동화할 수 있다는 이점이 있었습니다. 이를 통해 수동 배포 과정에서 발생할 수 있는 실수를 줄이고, 배포 시간을 단축할 수 있었습니다.
      </li>
    </ul>
  </div>

      </li>
    </ul>

<details markdown="1">
  <summary>Docker와 VM의 차이를 설명해주세요</summary>

VM은 하이퍼바이저를 통해 하드웨어를 가상화하기 때문에 VM마다 Guest OS와 독립된 커널을 가집니다. 반면 Docker 컨테이너는 운영체제 수준의 가상화 방식으로, 호스트 커널을 공유하면서 애플리케이션 프로세스를 격리합니다. 이때 namespace가 프로세스와 네트워크, 파일시스템 등 보이는 자원을 분리하고, cgroup이 CPU와 메모리 같은 자원 사용량을 관리합니다. 컨테이너는 Guest OS를 별도로 실행하지 않아 상대적으로 가볍고 배포와 확장에 유리하지만, 독립 커널을 사용하는 VM이 일반적으로 더 강한 격리 경계를 제공합니다.

      </li>
    </ul>

  <summary>Kubernetes Pod와 라이프사이클을 설명해주세요.</summary>
  <div>
    <ul>
      <li>
        Kubernetes의 Pod는 워커 노드라는 일꾼이 담당하는 작업의 최소 단위로, 쉽게 말하면 작업 지시서에 해당됩니다. 하나의 Pod 내부에 여러 컨테이너가 설정될 수 있습니다. Pod의 생명주기는 Pending → Running → Succeeded → Failed와 Unknown으로 이루어집니다. 우선 Pod는 작업이 이루어지기 위해 클러스터에서 승인이 이루어지고, 워커 노드의 kubelet에 의해 스케줄을 받게 됩니다. Pending  상태는 클러스터에서 승인이 이루어졌지만, 아직 스케줄링되기 전의 상태로, 컨테이너 이미지를 받는 시간도 포함됩니다. 이후 실질적으로 노드에 바인딩되는 상태가 Running입니다. Pod의 모든 컨테이너가 종료된다면 Succeeded 상태로 넘어가게 되고, 만약 종료 과정에서 하나 이상의 컨테이너가 정상적으로 종료되지 않았다면 Failed 상태가 됩니다. 그리고 이 외에 Pod를 실행하는 노드와의 통신 오류로 Pod의 상태를 조회할 수 없는 상태가 Unknown입니다.
      </li>
    </ul>

## 자료구조
<details markdown="1">
  <summary>문자열이 immutable인 이유를 설명해주세요</summary>
  <div>
    <ul>

<li>
문자열이 불변(immutable)인 이유는 크게 메모리 효율성, 보안, 그리고 멀티스레드 환경에서의 안전성 때문입니다.

첫째, String Pool을 통해 동일한 리터럴을 공유함으로써 메모리를 절약할 수 있습니다. <br/>
둘째, 파일 경로나 네트워크 연결 등 중요한 정보를 담는 객체로서, 외부에서 값이 변경될 위험이 없어 보안상 안전합니다. <br/>
셋째, 값이 변하지 않으므로 여러 스레드가 동시에 접근해도 별도의 동기화 처리 없이 스레드 세이프(Thread-safe)를 보장합니다. <br/>

결론적으로, 성능 최적화와 안정적인 시스템 운영을 위해 문자열을 불변 객체로 설계하는 것입니다.</li>
    </ul>
  </div>
</details>
<details markdown="1">
  <summary>HashMap과 TreeMap 차이를 설명해주세요.</summary>
  <div>
    <ul>

<li>
HashMap과 TreeMap은 모두 데이터를 저장하고 조회하기 위한 Map 자료구조입니다. HashMap의 경우에는 Key 값에 Hash 함수를 사용하여 인덱스를 결정하고, 해당 인덱스에 데이터를 저장합니다. TreeMap은 이진 탐색 트리 중 균형을 맞추는 레드-블랙 트리를 사용하여 데이터를 저장합니다. 일반적으로 HashMap이 검색과 저장에서 빠른 성능을 보이고, 추가적으로 데이터가 정렬된 형태를 유지하거나 범위 검색이 빈번한 경우 TreeMap을 사용할 수 있습니다.</li>
    </ul>
  </div>
</details>
</details>
<details markdown="1">
  <summary>Queue와 Priority Queue의 차이를 설명해주세요.</summary>
  <div>
    <ul>

<li>
큐와 우선순위 큐는 데이터를 처리하는 방식의 차이로서 큐는 FIFO를, 우선 순위 큐는 중요도 기반의 우선순위를 따릅니다. 
일반 큐는 연결 리스트나 배열로 간단하게 구현이 되어 삽입, 삭제 모두 O(1)이 걸리는 반면, 우선 순위 큐는 우선순위가 높은 데이터를 빠르게 찾기 위해 힙과 같은 복잡한 자료 구조를 활용해 O(log N)이라는 시간이 걸리고 정렬을 위한 오버헤드가 발생합니다.
단순히 순서를 시뮬레이션해야 할 때는 일반 Queue를 사용하는 것이 직관적이지만, 대규모 연산에서 최댓값 추적이 빈번할 때는 트리 기반 정렬이 보장되는 PriorityQueue(Heap) 방식을 도입하는 것이 알고리즘 최적화의 핵심 전략입니다.
  .</li>
    </ul>
  </div>
</details>
<details markdown="1">
  <summary>Binary Search Tree를 설명해주세요. </summary>
  <div>
    <ul>

<li>
이진 탐색 트리(BST)는 모든 노드가 '왼쪽 서브트리에는 자신보다 작은 값을, 오른쪽 서브트리에는 큰 값을 가지는' 명확한 속성을 지닌 자료구조입니다.
이러한 정렬 특성 덕분에 중위 순회(In-order Traversal) 시 데이터를 오름차순으로 정렬된 형태로 얻을 수 있다는 장점이 있습니다.
트리가 균형을 이룬 상태에서는 탐색, 삽입, 삭제 연산을 O(log n)의 시간 복잡도로 처리하여 대규모 데이터 검색에 적합하지만, 정렬된 데이터가 삽입되어 트리가 한쪽으로 치우치는 최악의 경우 O(n)으로 성능이 저하될 수 있습니다
  .</li>
    </ul>
  </div>
</details>
<details markdown="1">
  <summary>Redis가 빠른 이유를 자료구조 관점에서 설명해주세요. </summary>
  <div>
    <ul>
<li>
Redis가 빠른 이유는 내부 자료구조를 효율적으로 사용하기 때문입니다. 모든 Key는 Hash Table에 저장되어 평균 O(1)로 조회할 수 있고, String은 SDS, Sorted Set은 Skip List처럼 자료형마다 다른 자료구조를 사용합니다. 또한 데이터를 메모리에 저장하는 In-Memory 방식과 싱글 스레드 기반의 I/O 멀티플렉싱으로 디스크 I/O와 Lock 비용을 줄여 높은 성능을 제공합니다.
  .</li>
    </ul>
  </div>
</details>


<details markdown="1">
  <summary>데이터베이스에서 인덱스가 빠른 이유를 설명해주세요. </summary>
  <div>
    <ul>
<li>
데이터베이스에서 인덱스는 주로 B-Tree나 B+Tree 구조를 가집니다. 해당 구조는 정렬된 구조에서 트리의 깊이가 균형을 이루는 균형 트리 구조이기 때문에 검색 시 일관되고 빠른 성능을 보장합니다. 특히 B+Tree 구조에서는 리프 노드 간 연결 리스트로 연결되어 있기 때문에 범위 검색에서도 높은 성능을 보입니다.
  .</li>
    </ul>
  </div>
</details>

<details markdown="1">
  <summary>검색 자동완성 기능 구현 시 어떤 자료구조를 사용하겠습니까? </summary>
  <div>
    <ul>
<li>
자동 완성 자료구조라면 문자열을 저장하기에 유리한 Trie 자료구조를 고려해볼 것 같습니다. Trie의 경우, 루트 노드부터 문자 단위로 일치하는 단어를 찾아가기 때문에 접두사가 동일한 문자열을 쉽게 찾을 수 있습니다. 또한, 사용자가 입력한 접두사까지 도달하는 시간은 접두사의 길이인 O(N)이고, 이후에는 해당 노드의 서브트리만 탐색하여 반환하면 되기 때문에 시간복잡도 면에서도 효율적이라고 생각합니다.
  .</li>
    </ul>
  </div>
</details>
<details markdown="1">
  <summary>랭킹 시스템 개발 시 어떤 자료구조를 사용하겠습니까? </summary>
  <div>
    <ul>
<li>
랭킹의 요구사항에 따라 자료구조가 달라지지만, 정확한 실시간 점수 랭킹이라면 Redis Sorted Set을 선택할 것 같습니다. Sorted Set은 내부적으로 Hash Table과 Skip List를 함께 사용합니다. Hash Table은 사용자를 빠르게 찾고, Skip List는 데이터를 점수 순서로 유지합니다. 따라서 점수 갱신과 개인 순위 조회를 일반적으로 O(log N)에 처리할 수 있습니다. 다만 Redis는 메모리 비용과 데이터 유실 가능성이 있으므로 RDB에 원본 점수와 변경 이력을 저장하고, Redis는 실시간 랭킹 조회용으로 사용할 것 같습니다.
  .</li>
    </ul>
  </div>
</details>
